# Общая база для всех сервисов

Вся инфраструктура PostgreSQL находится в этой директории. Сервисы получают
готовый `DATABASE_URL` и выполняют только запросы из своих repository.

Из корня демонстрационного проекта:

```bash
bash database/setup.sh
# Для доступа из локальной Wi-Fi сети:
DB_BIND_HOST=0.0.0.0 bash database/setup.sh
```

Скрипт запускает один PostgreSQL из локального образа `postgres:17`, создаёт
одну базу `orders_db`, пользователя `orders` с паролем `1234`, применяет миграции.
Все пять таблиц находятся в одной базе. Повторный запуск сохраняет данные
и пропускает уже применённые миграции.

- `postgres.sh` — запуск контейнера и ожидание готовности.
- `bootstrap.sql` — база, роль, права и таблица истории миграций.
- `migrations/001_initial.sql` — все пять таблиц проекта.
- `setup.sh` — последовательное применение ещё не выполненных миграций.

Новые изменения схемы добавляйте отдельными файлами, например
`migrations/002_add_order_comment.sql`. Не редактируйте уже применённые миграции.
Имена: три цифры, подчёркивание, описание из строчных латинских букв,
цифр и подчёркиваний, расширение `.sql`. Файлы выполняются по порядку имени.
Каждая миграция запускается внутри транзакции; не добавляйте собственные
BEGIN/COMMIT или команды, запрещённые в транзакции (например CREATE DATABASE).

История хранится в `infrastructure.schema_migrations`, отдельно от публичных
таблиц приложения. Пользователь `orders` не имеет доступа к этой схеме.
Ему выданы права чтения и записи на все таблицы проекта и права на SERIAL.
Новые таблицы, создаваемые администратором postgres в public, получают те же права.

Настройки Docker: `DB_CONTAINER`, `DB_VOLUME`, `DB_PORT` (по умолчанию 5433),
`DB_BIND_HOST` (по умолчанию 127.0.0.1). Они не меняют `app.env` сервисов.
При смене публикации порта существующий контейнер нужно пересоздать,
сохранив volume; процедура описана в корневом README.

Подготовку выполняет преподаватель один раз на компьютере с общей БД.
В репозитории команд этот каталог копировать не нужно.
