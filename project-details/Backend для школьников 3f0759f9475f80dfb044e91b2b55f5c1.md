# Backend для школьников

Разрабатываемый бэкенд представляет собой учебную микросервисную систему обработки заказа.

Система состоит из пяти независимых микросервисов, каждый из которых отвечает за отдельный этап обработки заказа и хранит собственные данные в отдельной базе данных.

Обработка заказа происходит последовательно. Пользователь создаёт новый заказ через UI, после чего запрос поступает в первый микросервис. Каждый сервис выполняет свою часть бизнес-логики, сохраняет результат обработки в собственной базе данных и передаёт необходимые данные следующему сервису через HTTP API.

В рамках полного сценария заказ проходит несколько этапов:

1. Создание заказа.
2. Проверка и резервирование товара.
3. Проведение условной оплаты.
4. Создание доставки.
5. Формирование уведомления о завершении обработки заказа.

После прохождения всех этапов первый сервис получает информацию о завершении процесса и обновляет итоговый статус заказа.

Таким образом, каждый микросервис одновременно выступает в двух ролях:

- предоставляет собственное API, которое могут вызывать другие сервисы;
- самостоятельно вызывает API другого микросервиса.

Каждый сервис имеет собственную модель данных и собственную таблицу. Сервисы не обращаются напрямую к таблицам друг друга и обмениваются информацией только через HTTP API.

Основной пользовательский сценарий выглядит следующим образом:

UI → Order Service → Stock Service → Payment Service → Delivery Service → Notification Service → Order Service.

На UI пользователь может создать заказ и затем увидеть его текущий или итоговый статус.

Основная цель проекта — на простом примере показать принципы клиент-серверного взаимодействия, микросервисной архитектуры, REST API, HTTP-запросов, работы с базой данных и интеграции нескольких независимо разработанных сервисов в единую систему.

Каждый сервис принимает `POST` от предыдущего сервиса и предоставляет два `GET`-метода для чтения данных (они не используются, нужны чтобы шкилу напрячь). `Order Service` отличается: создание заказа приходит от UI, а финальный статус обновляется через `PATCH`.

Скрипт генерации бд:

```jsx
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    product_name VARCHAR(255) NOT NULL,
    quantity INTEGER NOT NULL,
    price INTEGER NOT NULL,
    status VARCHAR(50) NOT NULL
);

CREATE TABLE reservations (
    id SERIAL PRIMARY KEY,
    order_id INTEGER NOT NULL,
    product_name VARCHAR(255) NOT NULL,
    quantity INTEGER NOT NULL,
    amount INTEGER NOT NULL,
    status VARCHAR(50) NOT NULL,

    CONSTRAINT fk_reservations_order
        FOREIGN KEY (order_id)
        REFERENCES orders(id)
        ON DELETE CASCADE
);

CREATE TABLE payments (
    id SERIAL PRIMARY KEY,
    order_id INTEGER NOT NULL,
    amount INTEGER NOT NULL,
    status VARCHAR(50) NOT NULL,

    CONSTRAINT fk_payments_order
        FOREIGN KEY (order_id)
        REFERENCES orders(id)
        ON DELETE CASCADE
);

CREATE TABLE deliveries (
    id SERIAL PRIMARY KEY,
    order_id INTEGER NOT NULL,
    address VARCHAR(255) NOT NULL,
    status VARCHAR(50) NOT NULL,

    CONSTRAINT fk_deliveries_order
        FOREIGN KEY (order_id)
        REFERENCES orders(id)
        ON DELETE CASCADE
);

CREATE TABLE notifications (
    id SERIAL PRIMARY KEY,
    order_id INTEGER NOT NULL,
    message VARCHAR(500) NOT NULL,
    status VARCHAR(50) NOT NULL,

    CONSTRAINT fk_notifications_order
        FOREIGN KEY (order_id)
        REFERENCES orders(id)
        ON DELETE CASCADE
);
```
